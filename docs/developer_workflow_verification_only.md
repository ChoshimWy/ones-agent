# 缺陷流程：先跑通验证，再区分修复与发布

## 基线已经通过

`Analyze and repair` 不等于每次都必须修改生产代码。如果当前 HEAD 已经包含修复，定向基线测试可能直接通过。此时继续要求“失败复现 + 新的生产改动”，会造成没有合理修改可做却不断进入 `Continue repair` 的循环。

新增本地验证分支：分析 → 定向基线通过 → 最终测试 → 独立只读 review → 本地验证完成。内部标记为 `verification_only`，界面明确显示没有实施生产修复、没有发布，并保留外部验证限制。它不等于缺陷已在用户安装的版本中解决，也不自动创建空提交或 PR。

该分支使用程序执行的测试结果，而非模型声称的“通过”。进入时要求工作区没有生产代码改动、仅有本次复现测试，基线与当前快照一致，复现文件哈希未变化。最终测试失败仍停在测试环节；review 发现可执行的代码或测试问题时，自动交回修复。此后界面显示“本地验证 · 含复审修正（不发布）”，不再声称没有代码改动。缺少原始安装包、签名设备或特定平台验证时记录限制，不冒充发布验收通过。

旧任务如果停在修复阶段，已保存通过的基线和复现文件，且没有生产改动，可以在原任务恢复后进入该分支，无需重新分析或人为制造改动。

## 改动文件清单

累计文件清单由实际 Git 工作区生成，不再要求模型准确复述累计改动。模型经常报告“本轮没有修改”，而 Git 仍包含上一轮加入的复现测试；这不应被当作 `snapshot_mismatch` 阻断。

仍检查真实 HEAD、路径范围、敏感内容、扫描期间快照变化以及只读阶段是否发生写入。普通修复流程仍需测试、review 与明确发布批准；本地验证分支不授予提交、推送、PR 或 ONES 状态修改权限。

## 回归覆盖

- 单仓库、多仓库：基线通过后跳过实施，执行最终测试与 review。
- 真实 Git 工作区及真实测试进程：已修复 HEAD、旧版 BLOCKED 断点恢复。
- 测试失败、review 代码问题不能被标为验证完成。
- 完成结果持久化及重新加载，缺少测试/review 或未经复审修正流程混入生产改动会被拒绝。
- 普通修复、批准及发布链路保持原有边界。

## Review 自动回修

独立只读审查发现 `unresolved_items` 后，流程把具体问题保存为 `system_review` 修订，在原任务、原 Codex 会话内继续实施，随后重新执行测试并再次只读审查。单仓库与多仓库采用同样的闭环；仅缺少回归用例时允许补充非冻结测试，不强迫修改已经正确的生产代码。

审查引用的根因、修复前后行为、影响范围及风险等级绑定程序已保存的上下文，不因模型换一种措辞重复这些字段而阻断。审查自己的问题、结论、外部限制仍完整保留；真实 Git 快照、只读约束、冻结复现文件和发布前证据校验仍然有效。

自动回修次数持久化，使用配置 `max_codex_attempts` 作为连续轮次上限。再次审查仍有问题且实际受测快照没有变化，或达到上限时，暂停并显示明确原因。反复点击继续不会重置额度；用户提供新的修订方向后才开启新的额度窗口，并保留累计次数。即使本轮没有文件修改，也先经过 TESTING 重新验证，不跳过持久化状态机允许的阶段。

只有外部设备、权限或安装包验证限制时，不自动进入代码修复。普通修复仍需显式批准才能发布；基线已通过的本地验证任务，即使补充了复审修正，也不会自动提交、推送或创建 PR。

旧版本因审查上下文字段不一致而停在 `Continue review` 的任务，可在原任务恢复后使用已保存的审查问题回修，不需要重新分析根因。

达到上限或无进展时，Review 页直接显示暂停原因与累计轮次，按钮为 `Continue repair`。点击仅打开续修确认框；用户可以补充修复方向，确认才通过版本校验后的修订操作开启新窗口。取消不会执行任何工作。续修会同时携带人工方向和最后一轮尚未入队的审查问题；不清零累计次数、不绕过发布批准。

多仓库审查按 `repository_key` 提供各自的 `tested_snapshot` 和 `final_tests`。组任务的顶层 `tested_snapshot` 为空，避免把主仓库的快照错误地与依赖仓库实际修复比较。真实快照校验仍由宿主执行，不根据模型文字声称通过。

续修确认框的回调只向任务监督器提交后台工作，不能等待整条修复流程结束。后台任务由现有 watcher 跟踪完成、错误和过期版本，运行期间持续刷新 AI activity，并阻止按钮或快捷键重复提交同一任务。
